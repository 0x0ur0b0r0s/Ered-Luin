# Nansen credit ledger

This package reserves a closed, versioned estimate for each attempted provider request. Every retry or page must use a new attempt ID. The ledger persists every allocation, including failed and unfinished requests, and never refunds, resets, or tops up the budget.

Initialize or open a ledger with an explicit absolute database path, budget ID, credit limit, and cost-profile version. Production state belongs outside this repository. The package has no default path and never recreates state when opening fails. Tests use temporary directories.

The only cost profile in G1a is nansen-2026-09-22-v1: TOKEN_SCREENER=1, FLOW_INTELLIGENCE=1, SMART_MONEY_NETFLOW=5. These are admission estimates from Nansen's [endpoint overview](https://docs.nansen.ai/api/overview), not proof of the provider's billed credits. The guarded HTTP client and typed endpoint adapters are described below.

Callers provide a SHA-256 fingerprint of an already canonicalized, credential-free request. The ledger stores only that fingerprint and bounded allowlisted completion metadata. It never stores request bodies, headers, credentials, or raw errors.

A charge above its reserved estimate is recorded as a higher debit and permanently halts new reservations until an operator investigates. There is no operator reset or top-up API in G1a.

The implementation uses Node's built-in node:sqlite / DatabaseSync API. Node marks this API as a release candidate; production deployments must account for possible API changes and keep backups appropriate to the deployment.

Schema version 2 stores the aggregate allocation as a canonical decimal string, so a total beyond JavaScript's safe integer range remains exact. Per-attempt reservation and charge amounts remain SQLite INTEGER values. `getSnapshot()` raises `INTEGER_OVERFLOW` with an exact `allocatedCreditsExact` string diagnostic instead of returning a rounded number; new reservations remain blocked with `ACCOUNTING_HALTED`. Schema version 1 is incompatible and is rejected without migration or reinitialization.
## G1b guarded client and adapters

The public factory createNansenClient(options) returns the typed NansenClient methods tokenScreener, flowIntelligence, and smartMoneyNetflow. It requires an already initialized or opened NansenCreditLedger; it never opens, creates, resets, or repairs ledger state. The client defaults to enabled: false. It does not read environment variables, load credentials, or decrypt a stored key. Supplying enabled: true and an API key is an explicit opt-in; this repository still ships with NANSEN_API_ENABLED=false, a zero request budget, and paper execution.

The client uses only fixed POST paths at https://api.nansen.ai and the documented apikey, accept, and content-type headers. Callers cannot provide a URL, method, header set, operation cost, or endpoint override. The optional transport dependency supports deterministic fake transports in tests. The default transport rejects redirects, applies an 8-second timeout, bounds response bodies to 1 MiB, and retains only the allowlisted request ID and actual-credit-used response headers.

Before transport dispatch, the client canonicalizes the method, fixed path, operation, and JSON body without the credential, hashes that request with SHA-256, and commits one G1a ledger grant. Every page gets its own UUID attempt and reservation. There are no automatic retries. An absent or malformed X-Nansen-Credits-Used header remains unknown; the client never infers actual charges from the reservation estimate or account balance. A reported charge above the estimate invokes the existing G1a permanent halt.

The requests are deliberately limited to Base USDC and WETH evidence:

- tokenScreener sends chains: ["base"], a supported timeframe, explicit page parameters, and the two pinned token addresses. It sets include_stablecoins and include_native_tokens to true.
- flowIntelligence accepts only asset: "USDC" | "WETH" and sends exactly one Base token address per request. It uses the documented timeframe field.
- smartMoneyNetflow sends chains: ["base"], the two token addresses, explicit page parameters, and both stablecoin/native-token flags.

USDC is Circle's native Base contract, and WETH9 is listed in Base's official Base Mainnet contract table: [Circle's USDC contract listing](https://help.circle.com/support/en/usdc-supported-blockchains-minting-redemption-faqs?id=kb_article_view&sysparm_article=KB0010590), [Base contract addresses](https://docs.base.org/specifications/reference/base-contracts). Endpoint schemas and paths are maintained in [Token Screener](https://docs.nansen.ai/api/token-god-mode/token-screener), [Flow Intelligence](https://docs.nansen.ai/api/token-god-mode/flow-intelligence), and [Smart Money Netflows](https://docs.nansen.ai/api/smart-money/netflows). The 1/1/5 ledger estimates are listed in Nansen's [endpoint overview](https://docs.nansen.ai/api/overview); they remain estimates, not a provider billing guarantee.

Results expose bounded allowlisted rows, warning signals, page references, unavailable metric fields, and a three-state completeness value. Missing optional numeric fields are null, never fabricated zeros. Screener and netflow results are complete only after the provider signals the last page; an unknown page signal is returned as unknown, and a failed later page is incomplete with references to prior and failed attempts. Flow Intelligence has no pagination or explicit completeness field, so it reports unknown unless a provider warning makes it incomplete.

Default bounds are three pages, at most 20 pages, a 1 MiB response body (maximum configurable limit 2 MiB), an 8-second timeout (maximum 30 seconds), and a 64 KiB request body. Invalid or incompatible query fields fail before reservation. HTTP error bodies and raw transport exceptions are neither logged nor returned.

G1b adds no cache, observation store, polling schedule, background worker, application route, TypeSafe product call, or live Nansen request. Its synthetic JSON fixtures contain fabricated metric values and are not market evidence.

## G1c query management and offline collection

The query manager is the single query entrypoint for downstream callers and the collector. It requires the accepted G1b NansenClient and an already initialized or opened NansenObservationStore; it never creates or repairs either ledger. Its enabled option defaults to false. Its query is a strict object containing operation, asset scope, one-hour timeframe, page bound, retry bound, and per-page row count. The cache key is a SHA-256 digest of the canonical query, provenance, and schema version. Identical concurrent misses coalesce; a cache hit and a coalesced waiter do not add ledger allocations.

Provenance is derived at the client/transport boundary and is not a manager option. createNansenClient captures it from the same normalized configuration that selects the transport: only the package-owned fixed-host fetchTransport receives nansen; every injected transport receives synthetic. The marker is held in a private WeakMap, and structurally supplied clients that were not created by the factory fail closed to synthetic. Provenance is part of the cache key, so synthetic snapshots cannot be reused under the Nansen source namespace.

qualifyingSuccessfulRequests is computed only from the current query’s in-memory 2xx page references when the query used a factory-registered client with the package-owned fixed-host transport. Each reference is returned after its guarded request has finalized a G1a ledger attempt; stored source labels alone never qualify. This is a request count, not a billed-credit count; actual provider-reported charge remains the G1a attempt reportedChargedCredits and can be unknown. Synthetic clients, cache hits, and coalesced waiters contribute zero. A stale fallback can count only 2xx references from the current in-memory query; it never counts historical references from the fallback snapshot.

If a request has dispatched but observation persistence fails, the manager returns failed status, incomplete completeness, no observations, and every known attempt/page reference with status and charge metadata. It does not claim a cache hit or return old observations as current query output. G1a remains authoritative for allocated credits and attempt outcomes.

Only the later Base policy signals are normalized: screener market cap and price for USDC/WETH, WETH Flow Intelligence smart-trader net flow, and USDC/WETH one-hour Smart Money net flow. Duplicate rows are partial evidence. A missing asset produces `MISSING`; a returned asset with an absent, malformed, or ambiguous metric produces `PARTIAL`. Both use `value: null`; a complete numeric zero stays the string `"0"`. Flow Intelligence has no provider completeness signal, so its values stay partial/unavailable. USD uses signed integer micro-dollars. Conversion starts from JavaScript's shortest decimal representation and rounds ties half away from zero. Values too large to fit the bounded persisted decimal field become partial rather than being rounded or truncated.

For these endpoints, `observedAt` means the local time the response was acquired, and `fetchedAt` means the local time the final query attempt began. These APIs do not provide an event timestamp for the selected metrics, so neither field claims a provider event time. Stored metadata contains allowlisted observations, page/attempt references, completeness, unavailable field names, and safe failure codes. It does not retain request bodies, credentials, arbitrary headers, raw errors, or provider warning text.

The SQLite observation store has schema version 1. Initialization and open require an explicit absolute file path and store ID; initialization refuses existing files, and open never creates, resets, or migrates state. Configure production state outside the repository. Writes use one SQLite transaction with WAL, foreign keys, and full synchronous durability. The store retains historical snapshots across refreshes, prunes beyond seven days, and enforces bounds of 100,000 observations, 10,000 snapshot records, and 512 cache entries by default. A cache entry expires after five minutes for token screener and flow, or thirty minutes for Smart Money net flow. The separate freshness limits remain ten and thirty-five minutes. Expired data is never presented as complete; a last-good fallback is returned with every value nulled, `PARTIAL` quality, `incomplete` completeness, and the refresh failure.

The default query bound is one page and zero retries. A query may request up to 20 pages and two retries only when the manager and G1b client are configured with compatible maxima. Each page and retry re-enters the guarded client and gets its own G1a reservation and attempt ID. The manager limits one instance to eight distinct in-flight queries and limits per-page rows to 100. Its worst-case estimate is reserved operation cost × page bound × (retry bound + 1); `estimateWorstCaseCredits` exposes this value. The collector defaults off, starts only by explicit `start()`, runs screener and WETH flow every five minutes and Smart Money net flow every thirty minutes, never overlaps cycles, and skips missed intervals after downtime rather than catching up.

Synthetic fixtures and fake transports are used for all G1c tests. Synthetic results use `provider: "synthetic"`; they are not market evidence. G1c did not decrypt credentials, make a live Nansen or TypeSafe request, enable `.env.example` defaults, or change paper-only execution. TypeSafe was skipped because the query, freshness, and financial conversion semantics are explicit and deterministic tests settle them.

## G1d TypeSafe semantic shadow

`buildG1DEvidencePacket(results, { now })` maps only G1c's Base USDC/WETH screener, WETH Flow Intelligence, and one-hour Smart Money signals. It validates operation, asset, metric, `usd_micros` unit, normalized signal schema, query source, and acquisition/fetch timestamp agreement. The bounded packet carries signal UUIDs, endpoint/source, timestamps, age, quality, completeness, values, and SHA-256 provenance references. Missing, partial, stale, synthetic, duplicate, contradictory, and invalid inputs remain explicit; stale values are removed and absence never becomes zero.

`createG1DShadowEvaluator()` defaults to disabled. An explicit evaluation with `enabled: true` requires a key and an initialized/opened external SQLite audit store. The fixed TypeSafe endpoint and `jev-latest` alias use one versioned Noul question about whether a fresh complete Base WETH spot plus one-hour Smart Money flow combination suggests a specific next research question for a human. A Noul is a yes-probability, not a separate confidence score; deterministic freshness, completeness, arithmetic, budgets, and execution remain code-controlled. See the official [TypeSafe API](https://docs.typesafe.ai/api) and [Noul primitive](https://docs.typesafe.ai/primitives/noul).

There is no scheduler or retry. A single enabled evaluation can make at most one request; disabled evaluations make zero. Before dispatch the evaluator commits a bounded local `PENDING` audit entry. After interruption it remains unknown (`requestsMade: null`) and is never replayed automatically. Requests are limited to 24 KiB, responses to 64 KiB, and timeout is 8 seconds by default (maximum 15 seconds). The injected transport is the test seam. The default transport refuses synthetic or otherwise ineligible evidence. Credentials and raw response bodies are excluded from evidence and audit records.

Noul responses produce only the advisory routes `STORE`, `WATCH`, or `ASTRA_REVIEW`. The thresholds are uncalibrated, `automaticRouting` is false, and results carry `authority: NONE`. No policy decision, execution permission, request budget, or Nansen call can be changed by TypeSafe. G1d has not demonstrated semantic value or cost savings: tests use synthetic observations and fake replies only. Actual project-data requests made: zero. Default expected TypeSafe requests: zero; a future explicitly enabled eligible evaluation: one maximum. Provider price is not asserted; token usage is retained only when the response validates.

No live project packet or credential was submitted for G1d. A payload-specific review must inspect the exact serialized packet built from approved fresh public-safe observations and its request digest before any future live call; synthetic fixtures cannot stand in for that project packet. Evidence for such a check should include an approved payload, representative independent analyst labels, observed usefulness or failure modes, valid provider model/usage metadata, and an explicit privacy/sharing decision. G2 policy and all live trading remain separate gates.
